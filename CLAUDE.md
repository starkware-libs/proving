# Proving Monorepo — StarkWare Circle STARK Stack

This repository unifies StarkWare's Circle STARK proving stack into a single Cargo
workspace:

- **stwo** — the core, AIR-agnostic prover and verifier library.
- **stwo-cairo** — the Cairo CPU AIR, the Rust prover/verifier, and a Cairo verifier for
  recursive verification.
- **stwo-circuits** — a circuit DSL and a circuit-based STARK prover/verifier.
- **proving-utils** — end-to-end run-and-prove orchestration, recursive proof trees, and
  privacy proving CLIs.
- **stwo-air-infra** — the AIR code-generation toolchain that produces the generated AIR
  code consumed by stwo-cairo and stwo-circuits.

Soundness bugs are catastrophic and irreversible. An accepted invalid proof or a rejected
valid proof is a protocol failure with no recovery path.

## Priority Contract

All agent behavior is governed by this hierarchy. No exception, no override.

1. **SOUNDNESS & SECURITY** — Cryptographic correctness is absolute.
2. **PRODUCTION QUALITY** — All tests pass. All gates hold. No guardrail bypassed.
3. **PERFORMANCE** — Prover performance is a correctness property. Regressions block.

its layout, commands, and architectural decisions. These rules are path-scoped: the guide for
an area loads automatically as soon as you read a file in that area's crates — you do not need
to load it by hand.

## Global Conventions

### Criticality labels

Files and modules are tagged in the guide rules with:

- `[SOUNDNESS-CRITICAL]` — a bug breaks proof soundness (invalid proofs accepted or valid
  proofs rejected). Field arithmetic, constraints, FRI, PCS, verifier logic, OODS.
- `[SECURITY-CRITICAL]` — a bug breaks cryptographic security. Fiat-Shamir channels, Merkle
  commitments, proof-of-work.
- `[PERFORMANCE-CRITICAL]` — a regression is a blocking correctness issue. SIMD backends,
  witness generation.
- `[AIR-GENERATED]` — produced by **stwo-air-infra**; see below.

### AIR-generated code

Many files under the stwo-cairo and stwo-circuits component directories are generated by
**stwo-air-infra** and marked `// This file was created by the AIR team.` **Do not edit
generated files by hand** — changes are lost on the next generation. Change them via
stwo-air-infra (see the `stwo-air-infra-guide` rule).

## Operation Boundaries

### Forbidden (NEVER do these)

- Modify constraint definitions, field arithmetic, FRI parameters, the Fiat-Shamir channel,
  verifier logic, or the commitment scheme without human approval.
- Disable, bypass, or weaken any test, lint, or CI gate.
- Manually edit files marked `// This file was created by the AIR team.` — use stwo-air-infra.
- Add `unsafe` in a soundness-critical path without documented justification.
- Accept a paper–code divergence as "probably fine" without documentation and review.
- Reduce security parameters (blowup factor, query count, grinding bits).

### Supervised (state intent, get approval)

Before modifying ANY `[SOUNDNESS-CRITICAL]` or `[SECURITY-CRITICAL]` file:

1. Consult the relevant area guide rule (auto-loaded for the area) and load any math/review
   skill it points to.
2. Identify the paper section (or stwo core component) governing the logic.
3. State the mathematical invariant the change must preserve.
4. State how the change preserves it.
5. Identify the test that will verify this.
6. Get explicit human approval.
7. After the change: verify all tests pass; update the divergence log if needed.

### Autonomous (proceed freely)

- Read any file.
- Add/modify tests. Do not remove tests.
- Fix lint, clippy, formatting.
- Add documentation and benchmarks.
- Refactor within a module without changing its external interface or mathematical behavior.
- Modify dev tooling, scripts, and CI configuration.

## Loading Protocol

1. **Working in an area** → its guide rule in `.claude/rules/` loads automatically when you
   read a file in that area's crates (see Repository Map); no manual step needed.
2. **Touching soundness/security-critical math** → load the relevant math and review skills
   per `.claude/skills/_index.md`.
3. **Before modifying theoretically-grounded code** → read `.agents/papers/llm/INDEX.llm.md`,
   the relevant distilled paper file, and the paper-implementation divergence log.
