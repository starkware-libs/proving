# Guide: stwo-circuits (Circuit DSL & Circuit-Based Prover/Verifier)

A circuit DSL for defining arithmetic constraints via gates, a STARK prover for those
circuits, and a standalone STARK verifier. Built on the `stwo` core; depends on
**stwo-cairo** for Cairo AIR definitions and trace handling.

References: [Circle STARKs paper](https://eprint.iacr.org/2024/278),
[Cairo paper](https://eprint.iacr.org/2021/1063). For math, see the `stwo-core-guide` rule
and load the math skills in `_index.md`.

## Stack

| Layer | Technology | Notes |
|-------|-----------|-------|
| Language / Edition | Rust nightly, edition 2024 | let-chains; pinned per-crate in this monorepo |
| Hash function | Blake2s | Blake circuit components + Merkle commitments |
| Test runner | cargo test | `circuit-prover` and `stwo` built at opt-level 3 in the test profile |

## Key Architectural Decisions

1. **Gate-based circuit DSL** — a builder centered on `Context<Value>`, `Var`, and the
   `Gate` trait. A `Context` holds the gate list plus optional concrete `QM31` values. With
   `Value = NoValue` you build topology only; with `Value = QM31` you also compute witness
   values. `eval!(ctx, ((a) * (b)) - (c))` gives concise inline arithmetic.
2. **Gate trait** — each gate implements `check()`, `uses()`, `yields()`. Built-in gates:
   Add/Sub/Mul, PointwiseMul (per-limb QM31 mul), Eq (equality, yields nothing), Blake
   (Blake2s hash gate), Permutation (multiset equality), Output (marks a public output).
3. **Yield/use invariant & `guess()`** — soundness of the lookup argument requires every
   variable be yielded **exactly once**. `guess()` introduces an unconstrained
   prover-provided variable; `finalize_guessed_vars()` adds a trivial `x + 0 = x` gate for
   each so the single-yield invariant holds. `check_yields()` and `check_vars_used()` verify
   these invariants.
4. **Circuit components** — Eq, QM31Ops, Blake (Gate/Round/RoundSigma/G/Output), XOR
   (TripleXor32, VerifyBitwiseXor at 4/7/8/9/12 bits), RangeCheck15/16 — each with
   constraint evaluation and logup interaction.
5. **AIR code generation** — component evaluators/subroutines in `circuit_prover/src/circuit_air/`
   and `cairo_verifier/src/` are generated by **stwo-air-infra**; manual edits are lost.
6. **Stable Rust** — all crates except `circuit-prover` and
   `circuits-stark-verifier-examples` must compile on stable (CI-enforced).
7. **Optimized test profile** — `circuit-prover` and `stwo` compile at opt-level 3 even in
   test builds to keep Blake tests fast.
8. **Finalization/preprocessing** — `circuit_common` bridges DSL and prover:
   `finalize_context()` hashes constants (Blake) and adds their hash as public outputs, then
   pads Eq/QM31Ops/Blake components to powers of two (min `N_LANES=16`); `add_zk_blinding()`
   injects randomness for ZK; `PreprocessedCircuit::preprocess_circuit()` builds the fixed
   preprocessed trace.

## Metrics

The two primary metrics are **prover time** and **proof size**. Performance regressions are
blocking (Priority Contract).

**Prover time** — wall-clock of `prove_circuit()` (`circuit_prover/src/prover.rs`):
witness generation (`write_trace()`, heavily rayon/SIMD parallel, N_LANES=16) →
interaction trace (`write_interaction_trace()`) → STARK proving (`prove_ex()` from stwo).
No built-in timing; wrap with `std::time::Instant` or profile externally. Because
`circuit-prover`/`stwo` are opt-level 3 in tests, test-time measurements approximate release.

**Proof size** — measured in `u32` elements (×4 for bytes). `ProofInfo::from_config(&config)`
in `stark_verifier/src/proof.rs` computes a full breakdown without an actual proof:

| Component | Scaling |
|-----------|---------|
| `fixed` (salt, 4 roots, nonces) | constant (44 u32s) |
| `claim` | O(n_components) |
| `oods` | O(n_columns) |
| `fri_commitments` | O(log(trace_size)) |
| `fri_last_layer` | O(2^log_n_last_layer_coefs) |
| `eval_samples` | O(n_columns · n_queries) |
| `eval_auth` | O(n_queries · log(eval_domain)) |
| `fri_auth` | O(n_queries · Σ layer_depths) |
| `fri_witness` | O(n_queries · Σ 2^step) |

Per-query components dominate. Reducing `n_queries` shrinks the proof but lowers security;
increasing `fold_step` reduces FRI auth path size at the cost of larger FRI witnesses.

## Merge/Rebase conflicts in proof fixtures

Proof/fixture files (`test_data/**/*.bin`, serialized proof JSON like `cairo1_proof.json`)
are generated artifacts — a merged version is meaningless. Resolve conflicts by taking the
old (base) version rather than hand-merging; then ask the user whether to regenerate, and
only if yes regenerate (e.g. `FIX_PROOF=1`) and let regression tests confirm.
